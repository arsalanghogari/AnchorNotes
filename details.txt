Preface:
AnchorNotes empowers users to capture, organize, and revisit their ideas through text, photo, and voice support. Unlike traditional note-taking apps that simply store information, AnchorNotes emphasizes context: notes can be anchored to specific times or places, ensuring that the most relevant information resurfaces precisely when it’s needed. By blending flexible creation tools with intelligent reminders and location awareness, the app helps users reduce clutter, improve recall, and stay productive across academic, professional, and personal settings.

Introduction:
Description
From students to professionals, to anywhere in between, collecting information down is an essential part of life. AnchorNotes allows notetaking to be performed using text, photos, and videos. AnchorNotes serves as a hub for all forms of notetaking for daily life.
Features:
Note Storage:
Users can create and store as many notes as they want up to their local or cloud storage limit.
Note Creation:
New notes are created by pressing the “New Note” button on the home screen. Users can add voice memos, images, and text to their notes and format text with different font sizes and styles.
Note Search:
Users can quickly locate specific notes by searching through keywords found in titles or note bodies. Searching is also refined using filters like tags, creation/edit dates, or attached media (photos, videos, voice memos, and/or location data). This combination of keyword search and smart filtering ensures that important information remains organized, discoverable, and accessible whenever needed.
Note Organization:
Users can pin, tag, or attach locations to notes. Pinning notes places a note at the top of the home screen regardless of the time it was last modified. Tagging notes allows for easier search, serving as a filter for notes. Attaching a location to notes provides additional context for notes and also enables the geofencing-based reminder feature.
Built-In Reminders:
Users can choose to receive a notification for specific notes based on entering a certain location (geofencing) or at a certain time.
Note Templates:
Users can create, edit, and manage note templates (with page color, pre-filled text, sections, and formatting), which are stored in a list alongside a default example template.
Templates can be associated with tags or geofences, and when creating a new note, users can select from available templates, with location-relevant ones prioritized at the top of the list.

Glossary:
Tag
A user-defined label for categorizing notes.
Pin
Toggling a note to stay in a fixed, highly visible location for quick access.
Geofence 
A virtual boundary around a real-world location used to trigger location-based reminders.
Voice Memo
An audio recording attached to a note.
Template
A reusable note format with a predefined structure, format, or tag.
UI
Short for user interface – what the user sees when interacting with the application.
Context-Aware
Usage of time, location, and user activity to showcase the most relevant notes to the user.

User Requirements Specification (User Stories):
Note Reminders
Users will be able to receive a notification which redirects them to their note based on reaching a certain location or upon a certain time.
Note Storage
Users are able to view all the notes they have previously created in order to access them at their convenience.
Note Search & Filtering
Users will be able to search through their notes not only by content but also by tags, date created, and media attached.
Note Templates
Users will be able to create, edit, and select templates for their notes so that recurring note types are easier to manage and faster to create.
Note Map
Users will be able to view a map that shows all of their notes and their location if the note includes a location.

Date: Search functionality will look through the notes based on the date they were created and/or edited, and return the notes with dates closest to the user specified date.

The user specifies:
Page color

Optional associated tags
Optional associated geofence

When creating a new template, a user can select from a list of available templates
If a user is in a geofence tied to a specific template, those templates should appear at the top of the list
Notes created from a template automatically inherit any associated tags or geofences
Note Map
 A user selects the “Map” icon in the app
The user can specify:
The scale of the map (pinching and zooming along with a slider)
General search and filtering as well (date/time, tags, search for keywords, media)
The icons for the notes (note previews, dots, etc.)
When the user clicks on a note, the user can see a preview, and can choose to go to the note.

Scalability
The app should be able to support at least 1,000 notes without significant hit to performance.
Autosave
When the application is closed, the notes do not get deleted, and the user is able to immediately pick up where they left off.

Architectural Design
Block Diagram

Figure 4.1 — Block Diagram for AnchorNotes

High-level architecture (overview)
AnchorNotes is a modular Android app organized into three layers following MVVM + Repository with an event-driven reminders subsystem:
Presentation layer (UI)
Screens: Home (Notes list + Pinned + Relevant Notes), Note Editor, Search & Filters, Templates, Map (optional), Settings.
Technology: Fragment/Compose views + Navigation; observes ViewModels (LiveData/Flow).
Domain layer (ViewModels & Use-Cases)
ViewModels coordinate UI state and invoke use-cases.
Use-cases encapsulate app logic (CreateNote, AttachMedia, TogglePin, AddTag, SetTimeReminder, SetGeoReminder, RunSearch, GenerateRelevantNotes, CreateTemplate, etc.).
Data & Services layer
Repositories: NotesRepository, TagsRepository, TemplatesRepository, RemindersRepository, SearchRepository, LocationRepository.
Local storage: Room/SQL entities for Note, Tag, NoteTagCrossRef, Attachment (photo/voice), Reminder (time or geo, mutually exclusive), Template, Location.
Android services: Foreground GeofencingClient/Location, AlarmManager/WorkManager (time notifications), NotificationManager, MediaRecorder/MediaPlayer, Camera/Photo Picker.
Indexing: FTS (SQLit) for fast title/body search; metadata columns for tag(s), date range, hasPhoto/hasVoice/hasLocation flags.
Runtime connectors:
UI ↔ ViewModels (observer pattern)
ViewModels ↔ Use-cases (method calls)
Use-cases ↔ Repositories (synchronous/Coroutine calls)
Repositories ↔ Room DB and Android services (Location, Alarms, Notifications)
Event bus (SharedFlow): reminder triggers → “Relevant Notes” updates.


Architectural patterns & rationale
MVVM + Repository: standard Android architecture that isolates UI from data sources; simplifies unit testing, supports lifecycle awareness, and clean error handling.
Event-driven / pub-sub for reminders: geofence & time alarms publish events consumed by the Relevant Notes Engine; this minimizes coupling and ensures triggers work while the app is backgrounded.
Strategy pattern (ReminderStrategy): enforces one reminder type per note (time or geofence) via pluggable strategies with validation.
Decorator/Composite for attachments: attachments (photo/voice) extend a note without changing core note logic.
Repository facade around Room + Android services: single place to handle offline, retries, and permission states.
FTS index: supports fast search across large note bodies; filter flags avoid scanning blobs.


 Major components (with responsibilities)
HomeModule
Displays: All Notes (last-edited sort), Pinned section, Relevant Notes section.
Interacts with SearchBar, Tag chips, Filter sheet.
NoteEditorModule
Rich text (bold/italic/font sizes, checklists), photo attach, voice memo record/playback, location attach/update/remove, pin toggle, tag add/remove, autosave.
SearchModule
Keyword search (FTS) + filters (tags, date range, hasPhoto/hasVoice/hasLocation).
Returns ranked result set to Home.
OrganizationModule
Tag CRUD, pin/unpin; exposes tag suggestions and pinned list maintenance.
RemindersModule
TimeReminderEngine (AlarmManager/WorkManager) and GeoReminderEngine (GeofencingClient).
Emits ReminderEvents to Relevant Notes Engine; posts notifications; handles removal/cancellation.
RelevantNotesEngine
Subscribes to ReminderEvents; inserts/removes entries:
Time-based → auto-expire after 1 hour.
Geofence-based → remove on exit event.
TemplatesModule
Template CRUD (page color, pre-filled text/formatting, optional tag(s), optional geofence).
Template picker prioritizes geofence-relevant templates.
MapModule (optional)
Visualizes notes with locations; supports same search/filters; opens note preview.
Persistence & Indexing
Room DB with DAOs; FTS tables for title/body; derived columns for filters.
Platform Services Adapter
Location/Geofence, Alarms/WorkManager, Notifications, Media, Permissions.

Key data model (high-level)
Note(id, title, body, lastEditedAt, isPinned, hasPhoto, hasVoice, locationId?, templateId?)
Attachment(id, noteId, type {PHOTO|VOICE}, uri, duration?)
Tag(id, name), NoteTagCrossRef(noteId, tagId)
Location(id, lat, lon, radius?, placeName?)
Reminder(id, noteId, type {TIME|GEO}, triggerAt?, geoId?, status {ACTIVE|CANCELLED|FIRED})
Template(id, name, pageColor, prefilledBody, defaultTags[], optionalGeoId?)

Error handling & offline behavior (architecture-level)
Location attached while offline/no GPS: LocationRepository returns LocationUnavailable; UI shows non-blocking message and saves note without location; user can retry later.
Enter geofence while offline: event is ignored (design requirement); next location update outside geofence won’t retro-trigger.
Remove reminder: RemindersRepository.cancel(noteId) cancels alarms/geofences and deletes the Reminder row; Relevant Notes entry removed if present.
Single reminder enforcement: ReminderStrategy.setReminder(note) checks existing type; if conflict, returns ValidationError and shows UI error.
Autosave: Editor emits debounced SaveNote use-case calls; crashes/app restarts reopen last state from DB.
Permissions: centralized PermissionsManager; graceful degradation (no location features without runtime grant).


Component ↔ requirement mapping (traceability)
Note creation & storage → NoteEditorModule, HomeModule, Persistence (text, images, voice, checklists, autosave).
Pinned section / pin & unpin → HomeModule + OrganizationModule.
Tags (create/add/remove) → OrganizationModule + Persistence.
Location add/view/update/remove → NoteEditorModule + LocationRepository + MapModule (optional view).
Search & filter (tags/date/media/location) → SearchModule + FTS + derived flags.
Reminders (time / geofence; one type only) → RemindersModule + Strategy + RelevantNotesEngine + Notifications.
Relevant Notes dwell rules → RelevantNotesEngine (1-hour expiry for time; remove on exit for geofence).
Templates (CRUD, tag/geofence assoc, prioritized by geofence) → TemplatesModule + Picker logic.
Note Map (optional) → MapModule.


External libraries & Android APIs (anticipated)
Room / SQLite — local storage & indexing.
Coroutines / Flow — async & event streams.
WorkManager / AlarmManager — time-based reminders (reliable, doze-aware).
FusedLocationProvider + GeofencingClient — geofence attach & triggers.
NotificationCompat — lock-screen & heads-up notifications.
MediaRecorder/MediaPlayer & Photo Picker — voice/photo attachments.
Maps SDK — Note Map visualization.

Diagram


Figure 5.6 — Sequence diagram for “Pin/Unpin Note and Refresh Pinned Section”

Description of Interactions
User → HomeUI
The user taps the pin icon next to a note in the Home screen or within the Note Editor to pin or unpin it.
HomeUI → NoteEditor
The UI delegates this action to the NoteEditor, which manages the note’s editable state and properties.
NoteEditor → Note
The togglePin() method is called on the note object, switching its isPinned attribute between true and false.
Note → NoteEditor
The updated note object returns to the editor, reflecting its new pinned/unpinned state.
NoteEditor → NotesRepository
The editor requests the repository to persist the change by saving the updated note.
NotesRepository → Database
The repository updates the isPinned field in the Note table within the Room database.
Database → NotesRepository → NoteEditor
The database confirms the update, and the repository acknowledges successful persistence to the NoteEditor.
NoteEditor → HomeUI
The editor emits an event or callback notifying the UI that the note has been updated.
HomeUI → PinnedSection
The UI triggers a refresh of the Pinned Notes section to reflect the latest pinned/unpinned state.
 PinnedSection → NotesRepository → Database
The pinned section queries all notes where isPinned = true to update the list displayed at the top of the screen.
 Database → NotesRepository → PinnedSection → HomeUI
The query results are returned, and the pinned section updates the Home screen view accordingly.

Sequence Diagram — Map View: Show Note Pins and Open from Map
Purpose
This diagram models the process of how a user interacts with the Note Map feature to view and access location-based notes. It shows how notes with attached locations are retrieved and displayed as pins on the map, how users apply filters such as tags, date, and media type, and how tapping on a pin displays a preview with the option to open the full note.
The purpose of this feature is to provide a spatial view of notes, allowing users to quickly locate and revisit information based on where it was created or is most relevant.
Diagram

Figure 5.7 — Sequence diagram for “Map View: Show Note Pins and Open from Map”

Description of Interactions
User → Filters
User instantiates and populates Filters with members: tags, createdRange, editedRange, hasMedia, hasLocation = true, pinnedOnly = false.
User → MapService
User calls pinsFor(filters) to request pins for the current map view.
MapService → SearchService
search(query="", filters) is invoked to find notes that satisfy the Filters members, including hasLocation when set.
SearchService → NoteRepository
Retrieves candidates via repository calls such as list() or previously indexed references.
Returns noteIds[] that match tags, createdRange, editedRange, hasMedia, pinnedOnly, and hasLocation.
MapService → NoteRepository
Iterates over noteIds[] and calls get(noteId) for each to obtain Note with its attached Location.
Uses Location members name, lat, lng, and radius.
MapService → MapPin
For each note that has a Location, constructs a MapPin with members noteId and location.
MapService → User
Returns the array MapPin[] for rendering.
User → Filters
User modifies any of the Filters members (tags, createdRange, editedRange, hasMedia, pinnedOnly). hasLocation may remain true for the map.
User → MapService
Calls pinsFor(filters) again. Steps 3 through 7 repeat to refresh the visible pins.
User → MapService
On pin tap, user asks for the note tied to that pin using pin.noteId.
MapService → NoteRepository
Calls get(pin.noteId) to fetch the Note aggregate, including title, body, pinned, createdAt, updatedAt, and any Tag or Attachment as needed for a preview.
MapService → User
Returns the Note data to the UI so the user can preview or open the note.
Postconditions
All notes that contain valid Location data and satisfy the selected Filters are displayed as pins on the map.
Each MapPin corresponds to a specific Note object, linking its noteId and Location attributes.
Adjusting filters or zoom level dynamically updates visible pins using MapService.pinsFor(filters) without requiring a full refresh.
Tapping a pin displays a note preview, showing key fields such as title, body snippet, and updatedAt.
Selecting Open Note retrieves the complete Note from NoteRepository.get(noteId) and navigates the user to the note view or editor.
If no notes match the criteria, the system displays an empty map state.
If location permissions are disabled, the map remains accessible but without note pins or geolocation filters.
All map interactions (filtering, zooming, tapping) execute without data loss or disruption to other application modules.
